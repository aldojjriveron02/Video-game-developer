The Jam category — not Compo — is the correct one: Jam allows any pre-existing base code; Compo requires everything created from scratch in forty-eight hours by one person with source shared. With thirty-nine hours of pre-jam prototype work, Compo is disqualified — miscategorizing is a real trap. The LD rules state the ideal LD game "can be played right in the browser, in a few minutes, alone," and Defold's jam advice notes raters typically play each game three to ten minutes. The hangar's problem: it must onboard a cold player to build-and-deploy in under sixty seconds of that tiny window, and it is the highest-leverage screen — a confusing hangar kills the run before combat starts. The freeze problem is Kody Wildfeuer's diagnosis: feature velocity exceeding integration velocity — every un-integrated hangar feature compounds bug backlog, docs drift, and wiring mismatches. Community rules of thumb: start cutting at five-sevenths of the jam — about fifty-one hours in, Sunday around nine PM — and spend the last three-sevenths on maps, issues, and polish; have the core functional with two days left for polish and bugfix; never let feature creep eat the bugfix buffer — "something will definitely go wrong." LD explicitly permits bug fixes after the deadline, no new features, with a short changelog.

Validation — the final checklist with specifics. LD submission: screenshots uploaded to the LD site; binaries hosted on itch.io; opt out of Graphics or Audio voting categories if third-party assets are used; Jam category; use the Submission Hour; post-deadline changes are bug fixes only, disclosed in a changelog. The itch.io page: cover image required — animated GIF allowed but must avoid seizure-inducing effects; screenshots and GIFs recommended even for browser games; accurate metadata and tags, no tag spam; select ONLY platforms actually tested; AI Disclosure tag if generative-AI materials are used — worth reviewing since the build is AI-assisted; do not publish before the page is ready since first publish hits the Most Recent list once. HTML5 ZIP: index dot html at root, one thousand files max, five hundred megabytes extracted, two hundred per file, relative paths only, case-sensitive filenames, HTTPS for external resources; enable Mobile Friendly so mobile gets click-to-launch fullscreen. Butler deploy: push command with user, game, and channel; after first push tag the channel HTML5 Playable in browser; use userversion for explicit build numbers; push-preview and dry-run to inspect the diff; hidden flag stages a new channel without going live — ideal for freeze-candidate staging; backend processing can take thirty minutes for large builds — never do the final push inside the last thirty minutes. Hangar-specific validation: the spec acceptance criteria; the five-user gate — five fresh players complete build to deploy of the M3 VEX duel unassisted, on iPhone plus desktop; no dead ends; touch targets and pointercancel hold; schema canary passes; persistence round-trips through TMP to verify to LIVE.

The techniques — freeze-safe polish. Write the freeze down as a social contract — a HANGAR_FREEZE dot md with explicit allowed versus banned lists; verbal freezes get violated. Keep a deferred list with dates — every "one more hangar feature" idea goes there; most are impulses that won't be missed. Safe-candidate discipline: an early build halfway through so something can be submitted in the worst case; implement via butler hidden staging plus push-preview before every push. Single-seam theme work: our THEME_HOOK plus sixteen adapters is the correct pattern — ALL theme expression flows through the adapters, and adapters are data and config, never code changes during freeze. Data-only tuning: juice and feel numbers already frozen with a locked number sheet. Version-control rollback safety: every freeze push tagged so a broken late build reverts instantly. Sleep and triage: seven hours sleep minimum; if stuck on a minor bug too long, ask whether it matters and move on.
