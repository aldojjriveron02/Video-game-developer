Full report is in your Drive. The jam save findings. A jam save is the entire persistence story of a seventy-two-hour slice, and it runs in a hostile host. itch.io's official HTML5 docs state games run "by embedding an iframe pointing to your uploaded code," hosted in "a subdirectory on our HTML CDN" — a separate origin from itch.io, requiring relative paths. The implication: our localStorage lives on itch's CDN origin, not our game's page, and the frame is cross-origin-framed — exactly the storage context most vulnerable to browser eviction and tracking-prevention partitioning. LD's own community wisdom treats the deadline as the design constraint: the Ludum Dare Survival Guide devotes its last four-to-eight-hour block to "publish and submit," sets a milestone like "after the halfway mark I will not add any new features," warns "you definitely don't want to be looking for an exporter during Submission Hour," and when the deadline looms says: "Cut. Cut. Cut." And the freeze window is unforgiving: after the seventy-two hours close, judges rate the uploaded build for weeks; a save-breaking schema change or corrupted save discovered mid-rating cannot be hotfixed without violating jam rules. The conclusion: Export-primary — a user-held JSON file — is the only save we fully control across origin moves, browser eviction, tracking-prevention purges, and private-mode sessions. localStorage is a convenience cache, not the source of truth. Validation — the final save checklist with specifics. The round-trip test: create fresh state, play, save, reload page, load, deep-compare. Defensive load: getItem then null check; JSON dot parse inside try-catch since corrupted data throws; validate the parsed object before applying; apply defensively — health equals saveData dot health or one hundred. Version plus migration: include a saveVersion field starting at one; each release upgrades saves one version at a time via chained migration functions; test migrations with real save files from previous versions. Boot-time storage probe: MDN's documented feature-detection pattern; treat failure as "session only"; and never assume a successful setItem means the data is actually there — verify with getItem for load-bearing values, because Safari's private mode hands you a zero-quota store where setItem silently succeeds but getItem returns null.
