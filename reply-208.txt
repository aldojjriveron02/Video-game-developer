Abratabia's web game checklist: define final sign-off metrics BEFORE the jam — load metrics like total megabytes, request count, time-to-interactive, and runtime metrics like median frame time, ninety-fifth percentile, draw calls per frame. Run the final pass on a three-tier device matrix — low-end phone, mid-range, desktop. The synthesis for us: freeze perf sign-off at least twenty-four hours before the deadline window so thermal results have time to force changes.

Validation — the thermal protocol. NixieFX: pick a measurable frame budget — twelve-point-five milliseconds on an eighty-hertz display; measure three independent signals — in-game FPS meter, Chrome DevTools Performance panel, remote USB debugging on a real device; fix until all three agree — "single source of truth gets you lied to." Diagnose variants not fixes: A-B each change versus the same benchmark scene; if it doesn't move the bottleneck number, it's decoration. Their shipped case: thirty-four milliseconds to nine-point-four after fixing allocation patterns; draw calls two-twelve to forty-seven after atlases and batching. Abratabia: scripted CI sequence played headlessly recording frame stats; perf HUD with frame time, draw calls, heap; telemetry with percentile breakdowns — median, ninety-fifth, ninety-ninth — "tail frames are what players feel." Explicit memory budgets and a thirty-minute no-restart leak test — memory growth equals leak, flat equals GO. The thermal protocol: a phone can hold sixty fps for three to five minutes then start throttling, so test sustained ten-to-thirty-minute sessions, not thirty-second bursts. Target lower baseline than peak. If frame time creeps over fifteen to twenty minutes, the build fails a real session even if the first sixty seconds look perfect.

The techniques — last-mile polish. MDN's optimizing canvas: pre-render repeated objects on offscreen canvases; integer coordinates; never scale in drawImage — cache pre-scaled copies; layered canvases for static versus dynamic; context with alpha false when opaque; batch canvas calls; avoid shadowBlur; rAF; dirty regions; match canvas pixels to CSS size. NixieFX: zero steady-state allocation after warmup; avoid map, filter, forEach in hot loops; no object or array literals inside loops; helpers mutate caller-owned outputs; ring buffers over Array dot shift; pooled events; cap DPR at two — "single biggest win on high-DPR phones"; keep draw calls in the low hundreds; cull offscreen. GeneralistProgrammer: profile, fix, re-profile until budget met; diagnose CPU versus GPU by dropping resolution fifty percent; pooling up to sixty times faster with zero GC; dynamic resolution gives thirty to fifty percent GPU headroom; sixty fps is sixteen-point-six-seven milliseconds; mobile thirty fps is thirty-three-point-three. Arcadigo's traps: iOS Low Power Mode throttles GPU heavily — "judges playing on a throttled iPhone will see a slideshow regardless of your code"; in-app browsers perform worse than real Safari; never profile with DevTools open — it skews results.

What to avoid. Single-source measurement. Shrinking the feature to make a bad number look good instead of diagnosing. Unpooled steady-state allocation — GC stutters. Unbounded DPR — renders three times the pixels for nothing. Optimizing without profiling — wasting jam hours on non-bottlenecks. Assuming desktop numbers transfer. Last-minute "one more particle system" after sign-off. Testing only the fresh-boot sixty seconds. Profiling on desktop Chrome and assuming iPhone Safari matches — WebKit is not Blink.
