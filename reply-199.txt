The jam perf findings. Web-Standards.dev field guide: keep EVERY frame under ten milliseconds, not just sixteen-point-seven — the stricter internal budget leaves headroom, because anything exceeding frame time reads as lag. Fixed timestep with render interpolation keeps logic consistent across hardware. NixieFX: sixteen-point-seven milliseconds is for EVERYTHING, including the browser's compositing overhead, not just game code. Their audit order when stutters appear: bound work to the visible window, then culling, then per-frame allocation, then pool prewarming, then lists rebuilt per frame, then render passes measured separately. Rule: profile on a real device — "don't shrink the feature to fake the numbers." Steve Losh, LD34 postmortem — solo dev, seventy-two hours, vanilla JS, zero budget. His perf line: "During the last day I spent an hour or so using a profiler to identify the hottest spots." Also: a jam is not the time for new tech, and "releasing before the end" — test-deploy before the deadline, because perf problems are discovered at deploy, not in dev.

Validation. VolumeShaderTest's iPhone GPU protocol — the only mobile-thermal protocol found: phones throttle GPU clocks after about thirty seconds of sustained load. Their rules: device fully cooled before the recorded run, Low Power Mode OFF, compare only the same mode against itself. Reference baseline on iPhone 15 Pro Safari: sixty average FPS, P10 fifty-six, ninety-three percent stability. Warning: ignore benchmark sites that don't standardize cool-down. Chrome DevTools: the Performance panel records frame-by-frame with orange and red flags on jank; the FPS meter gives a live estimate. Real-device workflow: Android over chrome-inspect, iOS over Safari's Develop menu with a Mac. The combined checklist: cool the device, cable to the Mac, remote timeline, five-minute M3 soak, watch the frame graph after the thirty-second throttle onset, record P10 frame time — not just the average.

The techniques — last-mile, no pipeline changes. NixieFX checklist: cap DPR at about two — the single biggest mobile win; draw calls in the low hundreds; bake sprites into atlases; treat hot-path allocation as a correctness bug — zero steady-state allocation after warmup, no map or filter per frame, ring buffers instead of shift, never build strings every frame; pools that are BOUND, prewarmed to realistic peak, overwrite every field on acquire, and define cap behavior — drop the newest low-value effect when exhausted; watch transparent overdraw; audit UI hot paths like HP bars. MDN canvas: pre-render repeated sprites offscreen; integer coordinates; never scale inside drawImage; layer multiple canvases instead of redrawing everything; alpha-false on the context; batch draws; avoid shadowBlur whenever possible; avoid per-frame text; rAF never setInterval. Fixed timestep decouples sim cost from render cost so a heavy frame degrades smoothly.

What to avoid. Last-minute additions — Losh's "bad" list is headed by deadline features; every unprofiled addition in the final hours is a budget risk. Optimizing the wrong thing — don't cut visible quality to hit a synthetic number; measure render passes separately first. Unvalidated deploy environment — the itch build is a different runtime than dev; test the deployed build on a real device, cooled, power-saving off. Canvas traps: shadowBlur and per-frame text are silent frame killers. Pool without cap: un-prewarmed pools GC-hitch on first use.
