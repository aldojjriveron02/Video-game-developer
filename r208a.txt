GameDeveloper's jam tips: don't wait until the final hour; make the game playable and tested on the LD environment before submitting; keep scope tight so the final hours go to polish and perf, not features. Abratabia's web game checklist: define final sign-off metrics BEFORE the jam — load metrics like total megabytes, request count, time-to-interactive, and runtime metrics like median frame time, ninety-fifth percentile, draw calls per frame. Run the final pass on a three-tier device matrix — low-end phone, mid-range, desktop. Budget: bootstrap JS bundle under one hundred kilobytes compressed, interactive under Fast-3G throttle in under ten seconds. The synthesis for us: freeze perf sign-off at least twenty-four hours before the deadline window so thermal results have time to force changes. Validation — the thermal protocol. NixieFX: pick a measurable frame budget — twelve-point-five milliseconds on an eighty-hertz display; measure three independent signals — in-game FPS meter, Chrome DevTools Performance panel, remote USB debugging on a real device; fix until all three agree — "single source of truth gets you lied to." Diagnose variants not fixes: A-B each change versus the same benchmark scene; if it doesn't move the bottleneck number, it's decoration. Their shipped case: thirty-four milliseconds to nine-point-four after fixing allocation patterns; draw calls two-twelve to forty-seven after atlases and batching. Abratabia: scripted CI sequence played headlessly recording frame stats; perf HUD with frame time, draw calls, heap; telemetry with percentile breakdowns — median, ninety-fifth, ninety-ninth — "tail frames are what players feel." Explicit memory budgets and a thirty-minute no-restart leak test — memory growth equals leak, flat equals GO.
