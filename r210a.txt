The hangar is the riskiest screen of the submission: first interactive surface players touch, holds the most state — parts, saves, toggles — and sits inside hostile packaging constraints. LD's own embeds run in a strict sandbox: no localStorage, no external requests, fixed sixteen-by-nine at nine-forty-eight by five-thirty-three, mobile embed "might be sub-par" — and LD itself recommends hosting the game yourself and linking the page when a game needs external data. The submission hour is for packaging, not building: one extra hour after the seventy-two-hour clock, minor bug fixes only. Some jam hosts forbid updating the jam build after the clock at all. The last four to six hours must be reserved for submission prep and unexpected problems — the Survival Guide devotes the final four hours of a forty-eight-hour jam purely to publish and submit; scale to six of seventy-two. Validation — the five-user gate, grounded in Nielsen's classic. MeasuringU's history: the first four to five users find about eighty percent of problems, average single-user rate point-three-two, and severe problems are more likely detected by the first few — so the gate catches showstoppers fast. Koji's twenty-twenty-six guidance: about five users per segment finds eighty-five percent; explicitly run two to three small rounds instead of one big one. The protocol for our gate: one task per hangar job — build a deploy-ready mech with no verbal help, save and reload your build, find and use an assist toggle; unmoderated think-aloud, no hints; score task completion unaided, time to first deploy-ready, number of blocking errors; run three users, fix blocking issues — especially the MH-oh-eight actionable-error paths — then run the remaining two to confirm.
